实现已接入；真实 Private Blob、PostgreSQL 竞争和线上 GitHub Actions 尚未验收。不能据本文件声称线上资料已删除。当前 schema 仍为 `rr_0006`，复用既有 cleanup_jobs，无新增迁移。

## 保留规则

| 数据 | 行为 |
| --- | --- |
| 资料包 | 创建后 7 天到期，读取不续期；所有子资源均复查归属、删除和到期 |
| 未进入任何 revision 的上传 | 创建后 24 小时入清理；与保存版本使用同一 packet 锁；历史版本来源不会被视为孤立上传 |
| 主动删除 | 包立即 tombstone；账号额外停用账号、撤销所有会话和会员，待支付订单撤销；返回 `202 cleanup_pending` |
| 原件及派生内容 | 物理删除目标 24 小时；清除所有版本、页文字、证据、事实、事项、人工决定、草稿历史、快照；导出没有服务端文件缓存 |
| 在途执行 | 返回时再次检查 tombstone；结果丢弃，已发生供应商成本仍结算；失联任务 lease 到期恢复，未知费用保留 24 小时后按上界记估算费用 |
| 最小审计／限流 | 保留 30 天，维护分批移除；日志只输出错误分类及 request_id，不记录原文／供应商 body／token |
| 支付去重 | 最小事件和供应商订单 ID 保留 90 天；账号删除后先去掉用户关联及 checkout 回跳／URL；90 天后删除事件、清空供应商 ID，只留去标识化金额及费用统计 |

账号清理等待其包及在途账本处理完毕；期间账号始终停用。来源内容先清理，暂留无原文的 run/revision/packet 记录供未知费用结算；不会因为成本尚未确定而继续保存页文字和审核结果。清理账号后，同一 GitHub 身份可重新注册，但得到新账号 ID，旧订单不会给新账号发权益。找不到、已去标识化、超期订单的迟到事件拒绝处理。

## 每日维护

`.github/workflows/referral-maintenance.yml` 在每日 **03:17 UTC** 或 `workflow_dispatch` 执行 `scripts/referral_maintenance.py`。部署该 workflow 前需在仓库设置：

- `RR_MAINTENANCE_SITE_ORIGIN`：仅 HTTPS 站点 origin，不含 `/api/v1`、路径、查询或用户信息。
- `RR_MAINTENANCE_TOKEN`：与后端同名配置一致的专用 Bearer secret；不能使用登录 cookie 或 Stripe secret。

维护入口为 `POST /api/v1/internal/maintenance`，与 Stripe 是否启用无关。普通会话／CSRF 不能授权维护。输入 `{ "limit": 200, "cursor": null }`；返回 `processed / failed / exhausted / backlog / cursor`，不含对象键、账号 ID 或原文。`cursor: "continue"` 表示再次从持久队列取工作，不使用会因删除而漏项的 offset。

每批最多 200 个维护工作项，45 秒时间预算，在开始外部操作前预留其超时与提交时间；不会派发模型。一次工作项可以清理同包关联图，不代表最多 200 条 SQL。Stripe 恢复共享批次预算、使用请求上下文中的剩余时间限制 HTTP；存储沿用 30 秒超时，慢请求／DB 故障可能提前中断，由持久任务继续恢复。工作流最多 10 批，间隔 5 秒；请求最长等待 55 秒，不跟随重定向，不打印凭据或站点 URL。失败、达到重试上限或十批后仍有积压均以非零退出，触发 GitHub Actions 失败状态。仓库操作者需在自己的 GitHub 通知设置中启用 workflow 失败通知，并实测收到通知；当前未验证。

任务可能因供应商延迟、Actions 调度延迟、在途 lease 或未知费用暂时保留积压。24 小时是应用清理目标，不是平台 SLA；访问阻断不依赖调度。部署后必须实测每日调度及手动触发，不能以本地脚本测试代替。

## 故障补偿与人工恢复

对象删除前持久化 running 状态、尝试次数和 10 分钟 lease。删除返回成功并提交配额释放之后才标 succeeded；删除后 DB 提交失败时仍占用容量，lease 到期重试幂等删除。存储失败使用最长 60 分钟的退避，10 次后停止；DB 图清理失败回滚、记录 `PURGE_FAILED`，5 分钟后重试，10 次后停止。等待子任务不占用失败次数。

处理告警时先检查存储／DB 连通、部署配置和错误码，不读取或粘贴私人原文。对象恢复可显式执行既有 `python -m referral_review.documents.maintenance --limit 20 --retry-exhausted`（使用项目 `.venv`，在 backend 目录，配置由操作者提供）。包／账号任务的 exhausted 恢复需操作者审核选定 job ID，在事务内将该任务 `attempt_count=0,state='pending',next_attempt_at=当前UTC` 后重跑；不要删除 cleanup job 或手动减配额，不得对全部队列盲目清零。

应用产生的对象都先有 DB reservation 和 object cleanup intent；这里的孤立清理覆盖未保存到 revision 的上传、上传失败和写对象后 DB 失败，不扫描／删除 Blob store 中其他应用或手动上传的未知对象。

## 备份及已下载副本

应用删除无法撤回用户此前下载／复制的文件，也无法撤回已发送给供应商的请求。固定演示合成素材不属于个人资料。当前没有取得实际 Neon 项目的恢复窗口、Vercel Blob 副本以及 Vercel／GitHub 运行日志保留配置，因此**实际供应商备份保留期尚未核实，不承诺立即消除**。

MT-24 上线前记录所用项目／计划、控制台中的实际备份恢复窗口和日志保留、核查日期及操作者证据。应用 stdout 不在本仓库持久写日志，30 天应用日志目标仍需部署平台的实际日志／导出接收端设置验收。发布门槛不能把供应商默认值或文档值当成该项目已配置值。

## 手动验收

1. 使用合成资料创建两包并保存多个版本，完成一次人工审核和导出；删除其中一包后，用旧 URL 访问原件、页文字、run、历史及快照，均应 404，另一包可继续使用。
2. 在账号页输入 DELETE 并提交，验证所有浏览器会话失效；界面只能说明清理已排队。手动运行维护，确认实际 Blob 消失、配额回收及 backlog 清零。
3. 在隔离测试环境注入存储／DB 故障，检查失败状态和失败通知；恢复后重跑，验证不会重复扣减容量或恢复被删除内容。
4. 用 Stripe 测试事件核查删除前后的重复／迟到付款都不能恢复会员；记录真实供应商测试证据。

这些步骤未自动操作浏览器，也不授权真实 AI 调用、付费操作或删除用户现有生产数据。
